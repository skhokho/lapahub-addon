## Changes

- Scene commands check the original expiry again after waiting for the scene
  lock and after HA lookup/definition restoration. An expired activation never
  dispatches `scene.turn_on`; an expired deletion does not suppress the saved
  definition. The durable receipt reports `expired`, and redelivery does not
  repeat the operation.
- Creation/update and deletion reject imported HA scene IDs before dispatch.
  Previously an edit to `scene.evening` could create `scene.lapahub_evening`
  while the cloud still referenced the original scene. Companion backend
  validation rejects these unsupported mutations while retaining activation.
- Addon CI now compiles `managed_scenes.py` as well as the executor and command
  journal modules.

## Supervisor build compatibility — 28 October 2026

Version 1.0.55 corrects an observed Supervisor/Docker build failure before addon
startup: the old Dockerfile required `BUILD_FROM`, but the running Supervisor
invoked the build without that argument. The image now has a pinned Home
Assistant Alpine 3.22 multiarch default for amd64/arm64 and explicit architecture
base-image mappings in `lapahub/build.yaml`. Registry manifests for all five
previously declared architectures were inspected successfully; this is manifest
availability evidence, not runtime certification of the legacy architectures.

Runtime dependencies use matching Alpine binary packages, including psutil and
PyYAML. This avoids a native pip compilation requirement and bundles the public
`config.yaml` needed for offline version reporting. The addon slug, options,
command journal, scene database and Python business logic are unchanged.

The 30 existing tests and compilation of the three application modules pass.
The added `image-smoke` CI job builds the actual image without `BUILD_FROM`, then
runs with networking disabled. It imports the application, checks bundled
version fallback, and exercises integrity/reopen/no-replay behavior for both
SQLite classes in an isolated temporary directory. It never mounts the live
`/data` directory or calls an HA service.

The local managed executor has Docker access and verified GHCR manifests, but
its enforced network policy does not include Alpine package repositories. A
complete local image build is therefore not claimed. Require the real GitHub
image-smoke job and the authorized ARM64 HA build/runtime checks before claiming
that this packaging correction is validated on the installed addon.


### 28 October — Supervisor pinned-base correction (1.0.56)

Actual ARM64 Supervisor evidence showed that build.yaml rejects digest-suffixed
image names, warns that build.yaml is deprecated, and injects BUILD_FROM=latest.
Version 1.0.56 removes build.yaml and declares all five immutable architecture
base stages directly in Dockerfile. BUILD_ARCH selects the pinned-base stage;
BUILD_FROM is deliberately unused, so an injected latest value cannot override
the pin. No Python business logic, options, slug or database paths change.

Real local Docker builds of target pinned-base succeeded for amd64, aarch64,
armhf, armv7 and i386, each using its correct platform and with an explicit
BUILD_FROM=ghcr.io/home-assistant/base:latest argument. Build output resolved
only the selected pinned 3.22 base. These are base-selection checks, not
application runtime certification. All 30 tests and Python compilation passed.
CI additionally builds the pinned-base target with the adversarial override,
then retains the full image build and isolated import/SQLite smoke gate.
Full image CI and actual ARM64 Supervisor runtime evidence remain required;
local Alpine network restrictions remain unchanged.


### 29 October — Source report freshness (1.0.59)

Read-only runtime evidence showed a finite zero power value with HA last_reported
00:08:14Z still present in fresh HA snapshots after 01:00Z. The previous adapter
re-stamped it with fetch time, proving snapshot availability but not current
source-report freshness. This does not establish that the physical zero is wrong
or diagnose a device failure; a related source continued reporting. No private
entity identifiers, configuration values or credentials are retained here.

Live power now requires an aware last_reported timestamp within 600 seconds of
the HA fetch and no more than 60 seconds ahead. This matches the existing cloud
observation window and two default 300-second addon cycles; producer cadence was
not proven, so it is a conservative qualification policy, not a fault detector.
Fresh reported zero remains measured zero even with old last_updated. Missing,
invalid, naive, stale or excessively future report timestamps produce null raw
power and omit every dashboard power path, including legacy source fields.
Qualified power retains its actual report time in observed_at. The top-level
time remains the snapshot fetch time. SOC and cumulative counters are unchanged.

Two new regression tests initially failed with nine assertion failures on the
old adapter. Expanded coverage includes exact bounds, timezone offsets, fresh
unchanged zero, legacy dashboard bypass paths, and unchanged SOC/counters. All
64 Python tests and compilation pass. Real image CI also exercises installed
fresh/stale power adaptation before the existing two-database reopen smoke.
Full image CI and actual installed 1.0.59 evidence remain release gates. This
addon change alone does not establish complete multi-source automatic aggregate
availability; backend expected-member qualification must be assessed separately.
