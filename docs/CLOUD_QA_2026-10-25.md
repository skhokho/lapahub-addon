## Changes

- Scene commands check the original expiry again after waiting for the scene
  lock and after HA lookup/definition restoration. An expired activation never
  dispatches `scene.turn_on`; an expired deletion does not suppress the saved
  definition. The durable receipt reports `expired`, and redelivery does not
  repeat the operation.
- Creation/update and deletion reject imported HA scene IDs before dispatch.
  Previously an edit to `scene.evening` could create `scene.lapahub_evening`
  while the cloud still referenced the original scene. Companion backend
  validation rejects these unsupported mutations while retaining activation.
- Addon CI now compiles `managed_scenes.py` as well as the executor and command
  journal modules.

## Remaining release gates

- Publish this branch and require green addon CI for the resulting commit.
- Deploy backend compatibility first; then install the addon on a designated
  fixture before distributing its compatible app. Preserve both
  `/data/command_journal.sqlite3` and `/data/managed_scenes.sqlite3`; never clear
  either database to retry an uncertain command.
- Verify the installed HA version's dynamic scene create/delete behavior,
  definition restoration after an isolated HA reload/restart and complete
  scene-member state reconciliation. A successful service receipt does not
  prove that every scene member reached its requested state.
- Phone, home-network and physical observation remain necessary for real
  latency, rapid interactions, dimming, offline/reconnect, partial physical
  failures and uncertain outcomes. Only KM office light is authorized for
  operation; do not restart the occupied home's whole hub or operate other
  devices. Use an isolated fixture for destructive fault injection.

These mocked and cloud checks do not certify production readiness, physical
behavior, Apple Home performance parity or TestFlight availability.

## Supervisor build compatibility — 28 October 2026

Version 1.0.55 corrects an observed Supervisor/Docker build failure before addon
startup: the old Dockerfile required `BUILD_FROM`, but the running Supervisor
invoked the build without that argument. The image now has a pinned Home
Assistant Alpine 3.22 multiarch default for amd64/arm64 and explicit architecture
base-image mappings in `lapahub/build.yaml`. Registry manifests for all five
previously declared architectures were inspected successfully; this is manifest
availability evidence, not runtime certification of the legacy architectures.

Runtime dependencies use matching Alpine binary packages, including psutil and
PyYAML. This avoids a native pip compilation requirement and bundles the public
`config.yaml` needed for offline version reporting. The addon slug, options,
command journal, scene database and Python business logic are unchanged.

The 30 existing tests and compilation of the three application modules pass.
The added `image-smoke` CI job builds the actual image without `BUILD_FROM`, then
runs with networking disabled. It imports the application, checks bundled
version fallback, and exercises integrity/reopen/no-replay behavior for both
SQLite classes in an isolated temporary directory. It never mounts the live
`/data` directory or calls an HA service.

The local managed executor has Docker access and verified GHCR manifests, but
its enforced network policy does not include Alpine package repositories. A
complete local image build is therefore not claimed. Require the real GitHub
image-smoke job and the authorized ARM64 HA build/runtime checks before claiming
that this packaging correction is validated on the installed addon.
